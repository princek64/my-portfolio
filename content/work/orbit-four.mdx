OrbitFour is a domain registrar. Customers use it to search for domain names, register them, set up DNS, move domains between registrars, and manage renewals and billing. There's a customer portal and an admin portal, both in the same codebase.

I worked on it from early 2022 to mid-2025. I built most of the frontend and a good part of the backend.

## The brief

OrbitFour was a new product, so there was no old system to replace. The job was to build a registrar from scratch that covers the whole life of a domain, from search to renewal, plus the tools the team needs to run it.

## What I built

### The customer portal

The customer portal covers everything from finding a domain to looking after it. You search for a name, add it to a cart and pay through a multi-step Stripe checkout. After that you manage DNS records, nameservers, DNSSEC, auto-renew and domain locking, and move domains in and out.

### Domain transfers

I built the transfer flow, which has its own set of screens: starting a transfer, the confirmation emails, tracking its status, and moving a domain between two accounts on the same platform.

### The admin portal

The admin portal gives the operations team a view of every domain, user, transaction, dispute and audit log. Admins manage products, TLD pricing, system messages, user permissions and the login settings for the registry connection.

## How it's built

Nuxt 2 (Vue 2) with Tailwind CSS on the frontend. The backend is Express, running inside the same Nuxt server, with Sequelize talking to PostgreSQL. Stripe handles payments and subscriptions, and emails go out through SendGrid and SES. It runs on AWS ECS, with S3 for files and short-lived download links for invoices.

A few parts of the build worth calling out:

- **One form pattern for everything.** I built the shared UI components: buttons, forms, tables, modals, cards, alerts and so on. Most data entry runs through one `Form` component. You give it a list of fields and a Yup validation schema, and it renders the right inputs and handles validation and submission. Each field type plugs in without the form needing to know about it.
- **Moving from Bootstrap to Tailwind.** The project started on Bootstrap-Vue. I led the move to Tailwind, one screen at a time: login, dashboard, domain settings, wallet, user settings and the admin panels. I set up the Tailwind config with our own blue colour scale, and added a lint rule for class order so the whole team wrote Tailwind the same way.
- **Permissions.** I built a small helper that checks a user's role against a permission like `view:export-csv` or `edit:product-pricing`. The admin portal uses it to show or hide controls, so each person only sees what they're allowed to change.
- **Grace periods.** The store works out where each domain is after it expires: still renewable, restorable, or past recovery. The screens use that to show the right options.
- **Talking to the registries.** Domain registries use a protocol called EPP. The portal talks to a separate EPP service through an authenticated API for DNS, transfers and DNSSEC. Some of those actions take a while, so the portal listens for a callback when each one finishes.
